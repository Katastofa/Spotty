# sim — симулятор походки Spotty

Первый рабочий слой симулятора: прошивка считает траекторию, PyBullet считает
физику, простой оптимизатор подбирает параметры походки.

```
code/spotty_config.h ─┐
code/gait_test/*.ino ─┴─> hostcheck/build.sh trace ─> traj.csv (12 каналов, тик 3 мс)
                                                          │
                          spotty_sim/model.py ─> spotty.urdf
                                                          │
                                                          v
                                         spotty_sim/player.py  (физика + метрики)
                                                          │
                                        ┌─────────────────┼─────────────────┐
                                     view.py          learn.py        sensitivity.py
                                   смотреть глазом   подбор параметров  свип по ПРИНЯТОМУ
```

**PyBullet не знает о походке.** Он получает 12 углов на тик и отвечает только
на вопросы физики. Питоновской копии `gaitPose`/`legIK` не существует —
требование R1 из `SIMULATION.md`. Любая правка `gait_test.ino` доезжает до
симуляции сама.

## Что нужно

```
pip install pybullet matplotlib
```

Для пересчёта траектории нужен стенд `hostcheck`. На Linux/macOS он собирается
сам (`bash`, `g++`). На Windows положен готовый `bin/trace.exe`, собранный из
ТОГО ЖЕ `gait_test.ino` кросс-компилятором — пересобрать его можно командой
`hostcheck/crossbuild.sh trace ../sim/bin` там, где есть mingw-w64.

## Команды

```bash
python verify.py                 # ворота: URDF и legIK прошивки — одна нога
python diagnose.py               # лесенка абляций: что именно роняет робота
python learn_shift.py --height 150   # ФАЗОВЫЙ СДВИГ КОРПУСА (цель §0)
python robust.py --height 150    # повторяемость набора по сетке ПРИНЯТЫХ чисел
python measure_cost.py           # ЦЕНА НЕЗНАНИЯ: что даёт каждый неснятый замер
python run_once.py span=40 vel=90        # один прогон, числа в консоль
python run_once.py --gui --params results/best_trot_seed1.json
python view.py                   # ОКНО С ПОЛЗУНКАМИ — смотреть, как меняется походка
python learn.py --gait 0 --gens 22       # обучение (подбор параметров)
python sensitivity.py --params results/best_trot_seed1.json
python compare.py --params results/best_trot_seed1.json
```

Ползунки в `view.py` двигают параметры ПРОШИВКИ, а не картинку. Всё, что видно
в окне, вводится в робота с клавиатуры:

| ползунок | команда робота | что это |
|---|---|---|
| `span`   | `P` | полуразмах шага, мм (полный шаг = 2·span) |
| `lift`   | `C` | подъём стопы в переносе, мм |
| `vel`    | `V` | заказанная скорость корпуса, мм/с |
| `swing`  | `W` | время переноса, мс |
| `height` | `H` | глубина стопы под осью хипа, мм |
| `shiftx` | `X` | сдвиг корпуса вперёд, мм |

**ВНИМАНИЕ про `trim`.** В декартовом движке `pTrimDeg` не участвует:
`gaitPoseCartesian` его не читает, трим живёт только в угловом движке. Сама
прошивка это знает и команду `b` в декартовом режиме отклоняет
(`angularOnly("b", "сдвиг корпуса в мм, 'X'")`), предлагая вместо неё `X`.
Стенд же ставит переменные напрямую, мимо разбора команд, — и поэтому
молча ничего не менял. Продольный аналог трима здесь `pShiftXMm` = `shiftx`
(команда `X`), поперечный — `pShiftYMm` (команда `Y`).

Период и duty — величины ВЫВОДИМЫЕ: их считает `recalcCartesianTiming()` из
`vel`, `swing` и `span`. Поэтому в окне они печатаются, а не крутятся.

## Фазовый сдвиг корпуса

`learn_shift.py` — опыт, ради которого симулятор и затевался (§0
`SIMULATION.md`). Прошивка НЕ меняется: стенд ставит её же `pShiftXMm` /
`pShiftYMm` перед каждым вызовом `gaitPose`, то есть проверяет, какой должна
быть таблица сдвига, прежде чем её заводить в прошивке.

Нужный сдвиг не подбирается вслепую, а считается: пока одна нога в переносе,
опора — треугольник из трёх стоп, и точка максимального запаса в нём — его
инцентр. Подбираются только масштаб, опережение и постоянный перекос.

## Обучение

Метод перекрёстной энтропии (CEM): насыпать облако вариантов, прогнать каждый,
взять лучшую четверть, сдвинуть облако к ней, повторить. Никакой нейросети:
подбираются те же шесть чисел, которые оператор вводит с клавиатуры, поэтому
результат можно прямо ввести в робота.

Что считается хорошей походкой — в `spotty_sim/evaluate.py`, класс `Weights`.
Там каждое слагаемое подписано; поменять веса — значит поменять, чему учится
оптимизатор.

## Какие замеры нужны и в каком порядке

`measure_cost.py` крутит каждое неизмеренное число по его коридору, оставляя
прошивке её собственные значения, — то есть меряет, насколько ответ модели
зависит от того, чего мы не знаем. Порядок замеров в `ЗАМЕРЫ_ПЛАН.md` получен
из этих прогонов, а не из общих соображений.

Шум метода — 69 мм пути: столько даёт разброс от возмущений, которых на
железе никто не заметит. Всё, что ниже, сигналом не считается.

## Чему тут можно верить

`SIMULATION.md` R3: у каждого числа есть статус. `learn.py` печатает таблицу
статусов перед каждым прогоном, и её надо читать.

* **КАНДИДАТ ПО STL** — бедро 108.31, голень 116.51, вынос хипа 10.75, стопа
  19.41, поперечная база 78.0. Берутся ИЗ ПРОШИВКИ, не переписываются здесь.
* **ПРИНЯТО** — продольная база (M4 не снят!), все массы, момент и скорость
  серво, жёсткость контура, латентность, трение. Их не мерили.

Продольная база в прошивке равна нулю, то есть НЕ ИЗМЕРЕНА. Симулятор без неё
считать не может и берёт 180 мм из коридора 135…232. Поэтому `sensitivity.py`
гоняет все три значения: вывод, который от этого переворачивается, — не вывод,
а свойство выдуманного числа.

## Чего симулятор не закрывает

Всё из §0 `SIMULATION.md`: нули M9, реальную динамику серво, люфт и изгиб
рамы, трение вашего пола. Плюс собственное: здесь нет обратной связи по IMU,
робот идёт вслепую, как и на железе.
